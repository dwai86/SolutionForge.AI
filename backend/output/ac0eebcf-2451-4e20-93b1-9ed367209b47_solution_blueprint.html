Delivery Plan – Multi‑Branch Inventory Management Platform (MVP)

Timeline constraint: 5 months (≈ 20 weeks) – all activities, buffers, and go‑live must fit within this window.
Approach: Iterative, MVP‑first Scrum (2‑week sprints) with a strong focus on delivering a usable core inventory ledger and alerting capability before adding UI polish and advanced reporting.

1. Delivery Overview

  • Recommended implementation approach:
  • Agile Scrum – 2‑week sprints, sprint‑planning, daily stand‑ups, sprint review & retrospective.
  • MVP‑first – build the minimal set of features that satisfies the confirmed business objectives (≥95 % inventory accuracy, 30 % stock‑out reduction, role‑based access).
  • Continuous integration & delivery – automated build, test, security scan, and deployment to Azure App Service slots (blue‑green).

  • Definition of Done includes unit‑test coverage ≥ 80 %, integration test pass, security scan clean, and performance benchmark met (< 2 s API response under load).

  • Major delivery phases (aligned to the timeline below):

  • Foundations & CI/CD – IaC baseline, repo setup, pipeline skeleton.
  • Core inventory ledger & ingest – DB schema, API CRUD, POS ingest function.
  • Low‑stock alerting – threshold config, alert function, email/SMS stub.
  • Simple demand forecast – nightly moving‑average job, forecast storage.
  • Frontend SPA & role‑based UI – React dashboard, inventory views, basic charts.
  • RBAC, audit & reporting – Azure AD group mapping, audit trail, CSV/Excel export.
  • Testing, performance & security validation – load test, penetration test, UAT.
  • Go‑live readiness & cutover – final readiness review, runbooks, production switch‑over.

11. Deployment and Release Strategy

  • Environment Strategy
  • Dev – Shared subscription, minimal scale (1 App Service instance, Basic PostgreSQL). Used for feature branches.
  • Test – Mirrors production scale (autoscaling enabled, Standard PostgreSQL) for performance & security validation.

  • Prod – Full autoscaling, geo‑redundant PostgreSQL standby, private endpoints, monitoring alerts, slot‑based blue‑green.

  • CI/CD Approach

  • Source: GitHub (or Azure Repos) → Azure DevOps Pipelines (YAML).
  • Trigger on PR (build + unit test) and on merge to main (full build, security scan, Docker image push to ACR, deploy to dev slot).
  • Manual approval promotes image to test slot → run smoke/performance tests → approval to prod slot.

  • Slot swap provides instantaneous rollback; previous version retained in staging slot.

  • Release Approach

  • Feature flags (Azure App Configuration) for optional toggling of forecast UI or alerting channels.
  • Each release includes DB migration scripts (Flyway) that are forward‑only and compatible with rollback via slot swap + DB backup restore if needed.

  • Release notes generated automatically from commit messages.

  • Rollback Considerations

  • Primary rollback: swap App Service slot back to previous version (seconds).
  • DB rollback: rely on point‑in‑time restore (up to 35 days) if a migration introduces incompatibility; otherwise forward‑only migrations are designed to be backward‑compatible for one version.

  • Infrastructure rollback: re‑apply previous Bicep version (idempotent).

  • Production Readiness

  • Runbooks: scaling, DB failover, alerting failure, incident response.
  • Monitoring: SLA dashboard (latency, error rate, alert delivery lag).
  • Post‑go‑live hypercare: 2 weeks of enhanced on‑call support, daily health check meetings.

13. Future Evolution (Post‑MVP)

  • Forecasting – Replace moving‑average with Azure Machine Learning pipeline (auto‑ML) for probabilistic demand forecasts; store models in Blob, serve via low‑latency endpoint.
  • Alerting Channels – Add Azure Notification Hubs for push notifications to a planned mobile app; integrate Slack/Teams webhooks.
  • Mobile – React Native app for store floor stock‑taking with offline sync (Azure Sync Framework).
  • Advanced Analytics – Introduce read‑replica PostgreSQL or Azure Synapse for columnar workloads; build Power BI dashboard for turnover, GMROI, trend analysis.
  • API Management – Deploy Azure API Management to expose secure, versioned APIs for ERP/POS partners, with throttling, analytics, developer portal.
  • Microservices – Decompose monolith into domain‑specific services (Inventory, Forecast, Alerting) deployed to Azure Container Apps or AKS as team and scale grow.
  • Event Streaming – Replace simple Service Bus topics with Azure Event Hubs/Kafka via Event Hubs for real‑time inventory event feed to ML models.
  • Enhanced Security – Implement Just‑In‑Time privileged access, Azure AD Conditional Access policies, consider HSM‑backed keys via Azure Key Vault.
  • Compliance – Add controls for PCI‑DSS or ISO 27001 as business expands (e.g., tokenization of card data, detailed audit retention).

These enhancements can be phased in after the MVP is stable and the team has validated core performance and operational practices.

14. Key Delivery Assumptions and Open Questions

Assumptions (based on Business Analysis)
1. Initial MVP will support ≤ 50 stores and ≤ 5,000 SKUs – used for sizing Azure resources.
2. Existing POS systems will export sales data via CSV or simple API; no deep integration required for MVP.
3. Users will access the platform primarily via web browsers on desktop/laptop.
4. Network latency between stores and the selected Azure region (US East 2) is acceptable for near‑real‑time updates.
5. No offline operation required in MVP.
6. Azure subscription and necessary services (App Service, PostgreSQL Flexible Server, Redis, Service Bus, Blob Storage, Key Vault, Monitor) are available and can be provisioned.

Open Questions Requiring Clarification
1. Exact store/SKU count at MVP launch – influences DB size and autoscaling thresholds.
2. Desired forecast accuracy or acceptable error margin – determines whether moving‑average is sufficient or if ML is needed sooner.
3. Whether offline capability is required for stores with intermittent connectivity – impacts design of data sync strategy.
4. Specific integration points with existing POS/ERP systems (APIs, file formats, frequency) – defines the ingest function contract and any needed adapters.
5. Compliance or audit requirements beyond general data protection (e.g., PCI, ISO 27001) – may necessitate additional logging, encryption, or access controls.
6. Expected SLA for alert delivery latency (e.g., within 5 minutes of low‑stock detection) – drives alerting pipeline design and monitoring thresholds.
7. Preferred authentication method (Azure AD username/password, SSO via SAML/OIDC, or LDAP sync) – affects Azure AD app registration and user provisioning process.

Answers to these items should be obtained before Sprint 0 completes to avoid rework.
